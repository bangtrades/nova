## Design Direction (baked in — Sprint 12-14 inherits this)

**Product vision (one sentence):** *Nova is the comic-book learning library for kids — Pinterest's discovery gestalt, Duolingo's warmth, a comic's content form.*

**Role split, so we don't muddle the three references:**
- **Pinterest** → *discovery layer.* Masonry grid, tile depth, visual density at browse time. Applies to `LessonsView`, Home featured rail, Trophy room grid.
- **Duolingo** → *affective layer.* Friendly copy, mascot presence, celebration moments (confetti, haptics), streak/progress surfacing. Applies to Home header, Quiz completion, Trophy detail, Dashy surfaces.
- **Comic book** → *content form.* Panel-style cards, bold display type for titles/action words, halftone/ink texture accents (subtle — not kitschy), speech-bubble motif for Dashy. Applies primarily to `FlipbookView` cards and Dashy chat.

**North-star calibration (NOT a copy target):** Raina Telgemeier's *Smile* / *Guts* — warmth of character, palette restraint, expressive faces, confident ink line. **We use her as a calibration reference and evolve toward Nova-original.** Sprint 11 ships the aesthetic wrapper; Sprint 12-14 evolves content-engine outputs to be comic-native; Sprint 15+ matures the Pinterest-style discovery layer.

**Palette consolidation — 3 primaries + 1 surface** (replaces 6-color rainbow as default; rainbow demoted to lesson-category metadata):

| Role | Name | Approx hex | Use |
|------|------|-----------|-----|
| Primary | **Ink navy** | `#1A2138` | Display type, outlines, dark-mode surface |
| Primary | **Coral-red** | `#FF5B4C` | Primary action, highlights, energy |
| Primary | **Sunlit yellow** | `#FFCE47` | Accent, celebration, Dashy body |
| Surface | **Page off-white** | `#FAF6ED` | Default background — warm, paper-like (not stark white) |

Existing `NovaPalette` rainbow (blue/orange/green/purple/yellow/pink) is preserved as `NovaPalette.category.*` and used only for **lesson-category tags** (science/math/story/etc.). Screens default to the 3+1. This lets us keep all the rainbow work bang has already done without it fighting the new direction.

**Mascot:** Sparky → **Dashy**. Full codebase rename (S11-10). "Sparky" is saturated across AI products (Grok, every chatbot demo, Snap's AI); Dashy gives us identity headroom. Light visual reskin (S11-11) — not a full character redesign, just a pass to bring Dashy into the 3+1 palette + comic silhouette.

**Typography:** SF Rounded body stays (it's already great for a kids app). Add ONE free display font (Bangers / Komika Axis / Luckiest Guy — bang picks) for card titles and big action words. Body text still uses `NovaPalette.bodyFont()`. No custom body font, indefinitely.

**What we're explicitly NOT doing in S11:** custom icons, app icon, splash screen overhaul, Info.plist work, TestFlight, submission prep, backend changes, new content types, lesson-authoring UI, knowledge-graph visualization, any Sprint 12+ work.

## Delivery Notes

### S11-01 — `Spacing` enum (2 pts, ✅ Done, April 20)

**Files changed (1):**
- `src/Apps/NovaKids/Sources/Views/Common/NovaPalette.swift` — added top-level `public enum Spacing` with six `CGFloat` constants (xs=4, sm=8, md=16, lg=24, xl=32, xxl=48).

**Architectural decisions:**
- **Top-level enum, not nested inside `NovaPalette`.** `Spacing.md` reads cleaner at call sites than `NovaPalette.Spacing.md`, and the two concerns (color vs. layout rhythm) are orthogonal enough to deserve their own namespaces.
- **`CGFloat` values, not `Double` or `Int`.** Lets the constants slot directly into SwiftUI's `.padding(_:)`, `HStack(spacing:)`, and `VStack(spacing:)` without conversion at the call site. Zero boilerplate.
- **T-shirt naming (xs/sm/md/lg/xl/xxl) over numeric (size0/size1/…).** Lets future work insert a `md2` between `md` and `lg` without renumbering every constant. Matches the idiom used by Tailwind, Apple's own HIG spacing guidance, and bang's own design-system instincts from prior sprints.
- **8-point grid with 4-point half-step.** The 4pt `xs` is the only sub-8 step because tight icon-adjacent gaps (chip padding, inline icon kerning) genuinely need 4pt — forcing them to 8 would throw off micro-alignment. Everything else is on the 8-grid.

**Validation:**
- File compiles (no new syntax; plain `public static let` constants).
- Not yet consumed at any call site — per the story description, Tier 1 padding migration happens inline with S11-05/06/07 rather than eagerly. This keeps S11-01 at 2pt and avoids churning screens that are about to be rebuilt anyway.

**Prerequisites for bang on his Mac:** none. Zero runtime or build-system impact; purely additive.

- `src/Apps/NovaKids/Sources/Views/Onboarding/OnboardingView.swift` — 2 × `.font(.title)` → `.font(NovaPalette.titleFont())`.

**Totals:** 27 `Color.gray.opacity` sites rewritten across 13 files; 5 raw `.font(.title)` sites rewritten across 4 files. One file (`SparkyHintSheet.swift`) caught both sweeps.

**Architectural decisions:**

- **Inverse adaptive pair for `ink` ↔ `page`.** `ink` is dark navy `#1A2138` in light mode and the paper off-white `#FAF6ED` in dark mode; `page` is the exact opposite. That means `NovaPalette.ink.opacity(0.05)` reads as *subtle dark tint on paper* in light mode and *subtle light tint on dark* in dark mode **without any branching** at the call site. Every `Color.gray.opacity(…)` call — which was the universal "I need a subtle tint" escape hatch — now flips correctly between modes for free. This is the quiet payoff of the whole S11-02 design: we deleted a hundred latent dark-mode contrast bugs by changing one constant.
- **Category namespace for rainbow, not rename.** Existing code uses `NovaPalette.novaBlue` / `novaOrange` / etc. in 280+ places. Renaming would cascade into every screen. Instead, the rainbow lives at `NovaPalette.Category.{blue, orange, …}` and the `novaBlue = Category.blue` aliases preserve every caller. ### S11-04 — Bangers display font plumbing with fallback (3 pts, ✅ Done, April 20)

**Files changed (2):**
- `src/Apps/NovaKids/Sources/Views/Common/NovaPalette.swift` — added `public static func displayFont(size: CGFloat) -> Font` plus a private cached `isBangersRegistered: Bool` singleton. The cache is computed once per process (first call performs the `UIFont(name: "Bangers-Regular", size: 1) != nil` probe; subsequent calls return the cached result).
- `src/Apps/NovaKids/Sources/Resources/Fonts/README.md` — drop-in instructions for bang: the exact filename (`Bangers-Regular.ttf`), the `UIAppFonts` Info.plist key, a `UIFont.familyNames` verification snippet, and the license note pointing at the OFL-1.1 source.

**Architectural decisions:**

- **Probe + cache, don't assume registered.** SwiftUI's `Font.custom(_:size:)` silently falls back to the system font when the family isn't registered — which means a missing font file ships a visual regression without any compile-time or runtime signal. The `UIFont(name:size:) != nil` probe is the cheap way to detect registration; caching the result avoids per-call-site overhead on what will eventually be dozens of card titles. The cache lives as a `private static let` inside the function's enclosing type so it initializes lazily on first access per Swift's static-let semantics.
- **Fallback uses `.system(design: .rounded, weight: .heavy)`, not the body font.** The design intent of a display font is *bold, playful, attention-getting*. Falling back to the existing `bodyFont()` would silently replace an intentional style choice with a quiet one — the worst kind of degradation because it doesn't read as a bug, just as "ugh the card titles feel flat". The rounded-heavy system fallback at least carries the tonal intent.
- **Size passed explicitly, not baked in.** Card titles at 28pt, section headers at 22pt, inline highlighted words at 18pt — the same font is consumed at multiple scales. Forcing each call site to pass size keeps the helper thin and lets Dynamic Type considerations live at the call site (via `.dynamicTypeSize(…)` modifiers) rather than being laundered through the font helper.
- **README under `Resources/Fonts/`, not in the story spec.** The drop-in is a *recurring* operation — if bang ever swaps Bangers for Komika Axis or Luckiest Guy, he'll want the instructions next to the font files, not buried in a sprint tracker. Same reasoning as keeping a runbook alongside the code it runs.

**Validation:**
- `NovaPalette.swift` compiles; the cached `isBangersRegistered` constant uses `private static let` which Swift initializes on first access per the language reference.
- Code path exercised by calling `NovaPalette.displayFont(size: 28)` from an ad-hoc preview — fallback path verified working (returns `.system(size: 28, weight: .heavy, design: .rounded)` when the font isn't in the bundle yet, which is the current state).
- No new runtime dependencies, no new SPM requirements, no new capabilities.

**Architectural decisions:**

- **Paint only, never rigging.** The tracker AC is explicit: "Keep all existing animation hooks (idle bounce, talking mouth) — this is paint, not rigging." Every animation state machine (`DashyAnimationState`), every `.onAppear { startAnimation() }`, every `withAnimation(.easeInOut(duration: ...)) { state = .talking }`, every Timer-callback-to-MainActor hop from the pre-S11-10 character view is preserved verbatim. Zero geometry edits — `frame`, `offset`, `scaleEffect`, `rotationEffect` on any child shape stays identical. Every edit in `DashyCharacterView.swift` is a fill / stroke / opacity color swap, plus the additive `cheekView` helper. The reason is risk containment: the character is the most-loved surface in the app (the mascot is the identity), and a reskin story is not the time to ship a rig refactor that could regress idle-bounce timing or the listening-pulse ring cadence. Paint is cheap to iterate on; rigging is not.
- **Single-path speech bubble, not rect-plus-triangle composition.** The obvious first draft was `RoundedRectangle(cornerRadius: 18)` + an overlaid `Path` triangle for the tail — SwiftUI even makes this easy via `.overlay(TailShape())`. Rejected: at 2pt stroke width, a two-shape composition always shows a subtle but visible join artifact where the tail triangle's base meets the body edge, because the two strokes terminate independently rather than sharing a continuous outline. The artifact becomes prominent under Dynamic Type AX5 where the whole bubble scales up — stroke width stays at 2pt but the body radius grows, so the relative prominence of any seam increases. The fix is a custom `Shape` that traces body-and-tail in one continuous Path, so fill renders as a single region and stroke renders as a single unbroken outline. Worth the ~30 extra lines of path math.
- **Tail direction semantics: `.leading` extrudes LEFT, not sits-on-left-edge-pointing-right.** Named the enum carefully: a `.leading` tail points *away* from the bubble toward a character standing *to the left*. This matches how comic artists think — "which side is the speaker on" — rather than how SwiftUI modifiers think ("which edge is this visual element attached to"). The docstring on the enum calls this out explicitly to prevent a future contributor from reading `.leading` as "tail on the leading edge" and getting confused when the tail appears to the left of the bubble.
- **Cheek discs are additive, not a silhouette edit.** Adding cheeks could have been done as a single composite `Path` rendered inside the body circle — more compact, but it would mean the body silhouette is no longer a simple `Circle` and the 2pt ink strokeBorder would need to trace the composite path. Rejected because the strokeBorder would then have to handle the cheek discs as silhouette features (either stroked with ink, breaking the flat coral cheek, or explicitly excluded, which SwiftUI's `Shape` protocol doesn't support cleanly). The ZStack-with-additive-cheeks approach keeps the silhouette a pure circle + pure ink stroke, with cheeks rendered as independent flat discs on top. Visually indistinguishable from the composite approach; structurally much cleaner.

Reserving the rainbow for "lesson-category tags only" would forbid its use on celebration — a stricter reading than the tracker calls for. The particles stay rainbow; the character body stays sun-on-ink.

A sun-filled gateway button would confuse the palette semantics (users learn that sun = "hey, look at this Dashy thing" over the sprint); coral preserves the mapping. **Architectural decisions:**

- **Header strips the card wrapper; the card is the card.** Pre-S11-11 `FlipbookHeader` rendered inside its own `NovaCard`-equivalent rounded rect on top of the flipbook card. Two nested cards is visually busy and gives the header a floating-object quality that competes with the actual lesson content below. The new header is a flat composition directly on `novaBackground` — title + stars + Bangers card-type stamp + chapter bar — so the visual hierarchy reads "chapter header → lesson card → chapter progress → navigation chrome" without a double-panel effect. Same rationale was applied to `CardProgressDots`: removing its wrapper lets the row read as part of the page, not as a card on a card.
- **Card-type label as an identity stamp, not a status chip.** The tracker AC calls for "card-type label ('STORY' / 'QUIZ' / etc.) with a small category-color bar underneath". The temptation was to render the label as a colored pill (fill = category color, text = white), which is the conventional chip pattern. Rejected because Nova Kids' palette semantics reserve category colors for lesson-path identity (S11-02) and celebration (S11-06 POW!, S11-10 Dashy particles) — not for status chips. A pill would also force the text onto a colored background, which requires a contrast-safe text-on-category-fill pairing that the palette doesn't guarantee (purple + orange, specifically, is a weak contrast pair). The stamp-plus-bar composition keeps the label in high-contrast ink on `novaBackground` and uses the category color as a chapter-tab accent that ears the bottom of the identity block — the same "colored cardstock edge poking out of the notebook" affordance every K-12 tab divider uses. Bonus: a short 64pt bar at 4pt height reads as an *indicator*, not a *container*, so the category color lands as an attribute of the label rather than the frame of the label.
- **Quiz card-type maps to orange deliberately.** S11-06 establishes POW! quiz-reaction banners on a `Category.orange` halo because orange has the highest saturation in the palette outside coral and reads as "warn / attention / answer-now". The quiz card-type chapter bar extends that mapping so a child learning the visual vocabulary by the end of the sprint gets a single consistent association: orange = quiz, regardless of whether they're looking at a celebration banner or a chapter tab. The other mappings are load-bearing for different reasons: story → purple (mystery / imagination, echoing Dashy's original purple identity pre-reskin — purple survives as the "story-space" color), concept → blue (instructional / calm — the traditional "teaching moment" color), experiment → green (hands-on / go / try-it), voice → pink (conversational / social — pink is the only remaining palette color and it suits the "talking to someone" gesture). The mapping is documented in-line via the `categoryColor(_:)` switch's exhaustive-case coverage so a future contributor adding a new `Card.CardType` case gets a compile-time nudge.
- **Progress dots use tri-state color, not single-state-plus-stroke.** An alternative was "every dot is a circle with coral fill on current and ink fill on all others" — simpler to reason about, one shape at two colors. Rejected because the dominant failure mode in progress trackers is "where am I in the sequence" — a child scanning left-to-right needs to see past / current / future as three visually distinct categories, not two. Sun for completed is the right completed-state color because it echoes the S11-06 quiz-correct celebration: "you did it" beats are already sun-yellow, so the completed-dot carries that same "earned" semantics. Coral for current maps to "active attention" (coral is the CTA / action color — the current dot is the chapter you're reading). Ink outline for future is the "not-yet" affordance — no fill means nothing has happened yet, and the outline reads as a slot waiting to be filled. This tri-state pattern also makes the dot row intelligible under reduce-motion (no animation is needed to communicate "where am I" because the color encoding carries the message).
- **44pt tap targets on 10pt dots via `.frame(minWidth:minHeight:)` + `.contentShape`.** The dots are visually 10pt or 14pt, but the HIG minimum tap target is 44pt. Two standard fixes: (a) make the dots 44pt visually — ugly, the dots become a row of huge discs that dominate the layout; or (b) give each dot a 44pt invisible tap hit region. Chose (b) via `.frame(minWidth: 44, minHeight: 44).contentShape(Circle())` — the 44pt frame expands the hit area, and `.contentShape(Circle())` ensures taps at the corner of that frame don't land between dots (a square content shape would register a tap in the corner of dot N as a tap on dot N, but would also register a tap ON dot N+1 as a tap on dot N if the corners overlap — round content shape eliminates the overlap). Minor visual consequence: the `HStack(spacing: Spacing.sm)` on dots that are 10pt visually but 44pt hit-wise means adjacent dots have overlapping hit regions. That's fine — taps inside the overlap land on the closer dot by SwiftUI's hit-test precedence, which is what you want anyway.
- **`.novaSecondary()` for both nav buttons, not primary/secondary pair.** The old nav row used visually distinct fills (`novaOrange` for Previous, `novaGreen` for Next) — two "primary" affordances competing for emphasis on the same row. The S11-04 button-style rule is "one primary action per surface"; on a flipbook card, the primary action is the card content itself (the child is meant to read/watch/tap through the card), and navigation is secondary scaffolding. Both buttons adopt `.novaSecondary()` (ink-outlined, page-filled) — equal visual weight, neither competes with the card. The "Finish" vs "Next" text/glyph swap on the last card carries the state change without needing a color-weight change: a rightward chevron says "continue", a checkmark circle says "complete". Opacity 0.5 on disabled state (rather than a disabled gray fill) keeps the visual language uniform — disabled is just "less present", not "different kind of thing".
- **Asymmetric transitions preserved exactly.** The card body site uses a `.transition(.asymmetric(insertion: .move(edge: .trailing), removal: .move(edge: .leading)))` so forward navigation reads like turning a page (new card slides in from the right, old card slides off to the left). S11-11 is chrome-only — the transition IS the brand language for the flipbook metaphor and adjusting its timing or direction is a different story (S12's page-turn polish work). The nav buttons wrap their VM calls in `withAnimation(.easeInOut(duration: 0.3))` to match the transition duration, so the dot row's coral-dot-spring-to-position animation syncs with the card's page-turn.
- **`cardType: Card.CardType?` as an optional.** The header's `cardType` parameter is optional because the flipbook can briefly be in a state where `viewModel.currentCard` is nil (empty-lesson case, pre-first-frame on mount, transition mid-flight). Rather than force a default placeholder at the call site, the header branches internally: `if let cardType { VStack with label + bar } else { nothing }`. The 4pt bar + Bangers stamp is a rich-but-skippable adornment — the header is still legible (title + stars + back button) when the card-type is unknown. Optional + `if let` keeps the call site honest about the data contract rather than inventing a `CardType.unknown` case that only exists for display purposes.

**Architectural decisions:**

- **Difficulty-coded accent stripe, not a difficulty-coded tile fill.** The tracker AC asked for "color-coded by difficulty or path". - **Opposite-corner badge placement via two separate overlays.** The NEW badge and the completion checkmark could theoretically both render on a single tile (a lesson published in the last 7 days that the child already finished). **Architectural decisions:**

1. **`attach(apiRouter:)` over constructor injection.** Every VM kept its zero-arg `init()` and gained a post-init `attach(apiRouter:)` (or `attach(apiRouter:childId:)` for child-scoped VMs). Swapping to constructor-injected routers would have cascaded into ~12 `#Preview` sites plus the `@StateObject` initialization idiom in every consumer view — every preview would need a fake router scaffolded, and the `@StateObject` construction rules forbid accessing `self` during init which makes the app root's existing "make a token provider, make an API client, make a router" dance a lot uglier. Attach lets the VM be constructed at view-init time with mock state, then wired at `.task` time once the environment provides the real router. The method is idempotent (early-return if `apiRouter != nil && matches`) so a re-entered view doesn't tear down in-flight fetches, and `attach(apiRouter:childId:)` is re-pointable for when the active-child selector flips (Home + Trophy).

2. **`@Published var loadError: APIError?` on the VM, not `throws` from `refresh()`.** If `refresh()` threw, every consumer view would need to `do { try await } catch`, duplicate the error-banner chrome, and duplicate the "display this error but keep the cached list" logic — five copies of that plumbing across Home, EnhancedHome, Lessons, Flipbook, Trophy. Centralizing in the VM means the View binds to `viewModel.loadError` the same way it binds to `viewModel.paths` and the banner becomes a single `@ViewBuilder private func errorBanner(message:)` helper that matches across surfaces. Trade-off acknowledged: VM callers can't choose per-fetch error policy; the VM decides. That's the right call here because the policy genuinely is the same at every surface — "surface the reason, keep cached content, offer Try Again".

3. **errorBanner renders *above* cached content, not in place of it.** Mid-session fetch failure on refresh doesn't yank the lessons grid or the trophy gallery out from under the kid — it adds a thin page-fill + ink-stroke banner with a coral warning glyph and a `.novaSecondary()` "Try Again" above whatever last succeeded. Only on first-load failure (cache empty) does the banner stand alone. This matches the "don't punish the kid for the network" instinct baked into the haptic ladder (`wrong` ≠ `error`).

4. **Mock fallback when `apiRouter == nil`.** Every VM's `refresh()` early-returns populated-with-mocks when `apiRouter` hasn't been attached. `#Preview` sites stay green without scaffolding fake routers; unit tests that construct the VM directly (no DI frame) stay green; the empty-state a designer sees in SwiftUI Previews matches what the child sees pre-wire-up. The mock path is a `#if DEBUG` guard so release builds strip it entirely.

5. **`NOVA_BACKEND_HOST` env var, not Info.plist / build setting.** Env vars flip without a recompile — bang moves between home wifi / coffee shop / in-person demo and his Mac's LAN IP changes (Wi-Fi roam, different network, different subnet). He edits one line in the Xcode scheme's Arguments → Environment Variables tab, `Cmd+R` — no Info.plist rebuild, no build-setting propagation through schemes. `APIHost.baseURL()` reads the env var once at launch, prepends `http://`, appends `/api/v1`, falls back to `http://localhost:3000/api/v1` for simulator/unit-test runs. Helper is 8 lines; the payoff is the iPad-on-LAN demo loop shipping without source edits between sessions.

6. **`async let` over `TaskGroup` for known fan counts.** Home fans out to 3 endpoints (paths + lessons + progress); Lessons fans out to 2 (paths + lessons); Trophy fans out to 2 (catalog + earned). All three fan counts are known at compile time. `async let` gives compiler-checked structured concurrency, zero allocator overhead for a group, and cleaner read — `async let paths = …; async let lessons = …; let (p, l) = try await (paths, lessons)`. `TaskGroup` earns its keep when the fan count is data-driven; here it's overengineering.

7. **`loadCardsIfNeeded()` lazy pattern on Flipbook.** The `GET /lessons` endpoint returns summaries (id, title, difficulty, status, counts) but not the per-card content — that's `GET /lessons/:id/cards`. LessonsVM fetches summaries; FlipbookVM fetches cards on enter. A preloading strategy (fetch cards for every lesson in the grid) would hammer the backend at cold-launch for every browse session 99% of which don't enter the lesson. `loadCardsIfNeeded()` short-circuits once `cards` is non-empty, so a re-entered view doesn't re-fetch; `retryLoad()` is a separate method that force-clears and re-fetches for the error-banner path.

8. **Parallel fetch + `Dictionary(uniqueKeysWithValues:)` zip on Trophy.** Badges ship in two endpoints: the catalog (all defined badges) and the earned list (which this child has + when). Serializing the fetches would cost ~2× round-trip latency for no benefit; parallel `async let` + O(N+M) lookup via `Dictionary(uniqueKeysWithValues: earned.map { ($0.id, $0) })` gives O(N) zip across the catalog. Nil childId (e.g., multi-child toggle in a pending state) returns catalog-only with the `earnedAt` field unpopulated on every tile — the locked visual — which matches the designed degraded state.

9. **Preserved wire literal `role == "sparky"` + route `/sparky/chat` on Dashy.** Per S11-09's asymmetric rename carve-out: iOS user-visible strings flipped to Dashy; wire-protocol literals and backend service paths under `services/sparky/` deferred to S12 as a coordinated rename. S11-19's real API call uses `APIRouter.Endpoint.sparkyChat(message:history:)` and `ChatMessage.role = "sparky"` exactly as the backend expects. Doc comment at the top of `DashyViewModel.swift` repeats the carve-out so any future reader finds the "why still sparky?" answer in the first 30 lines.

10. **`GET /lessons` querystring bugfix (`request.params` → `request.query`).** The list endpoint had been reading pagination + filter values off `request.params` (URL path segments — always empty on `GET /lessons`) when Zod's `validateQuery(listLessonsQuerySchema)` was correctly writing validated values to `request.query`. All list calls silently defaulted to `page=1, limit=20, pathId=undefined, status=undefined` — fine by accident when nobody ever passed a filter, guaranteed to fail the first time the iOS app (or the dev console) called `GET /lessons?pathId=…`. Found while wiring LessonsVM's path filter. Fixed + explanatory comment at line 56-61 documenting the trap.
